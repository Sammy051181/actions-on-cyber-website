Daily SMB Cyber Intelligence Brief

Today’s SMB cyber lookout: Microsoft 365 login approvals, leaked automation tokens, and fake extensions

What small and medium-sized businesses should look out for today.

High Wednesday 05 August 2026, 15:31 UK time
Today’s look-out: Cloud account takeover and SaaS token leakage (Microsoft 365, automation tools, extensions)

What to look out for today

Three themes to put on your radar today:

  • Microsoft 365 “login approval” phishing where staff are taken to a real Microsoft sign-in page and asked to approve a code/device login they didn’t start.
  • Leaked automation tool tokens (n8n) that can grant access to workflows, data and downstream credentials if they’ve been accidentally committed to public code repositories.
  • “Evil twin” developer extensions (lookalike add-ons) that pretend to be legitimate tools and quietly send system/developer environment data out.

Why this matters to smaller businesses

SMEs increasingly rely on Microsoft 365, shared inboxes, cloud documents and automated workflows. If an attacker gains a valid cloud session/token, they may not need to “hack” your systems in a noisy way. The impact is still very real: invoice fraud, mailbox rule tampering, payroll/HR data exposure, and access to client files.

Warning signs

  • Staff report being asked to enter or approve a code, or “confirm a device sign-in”, especially after an email/SMS claiming an urgent security issue.
  • Unexpected MFA prompts or approval requests when the user is not logging in.
  • New mailbox rules or forwarding set up without a clear business reason (e.g., finance@ forwarding externally).
  • Automations/integrations behaving oddly: workflows firing at unusual times, new connections appearing, or missing data.
  • Developers/IT notice newly installed extensions that are “close but not quite” the expected name/publisher.

How attackers may exploit the situation

  • Microsoft device-code style phishing: attackers trick a user into approving a sign-in on Microsoft’s real pages, which can result in access tokens that allow entry to email, documents and other cloud resources.
  • Token exposure (n8n): if an API token is leaked publicly (e.g., pasted into code or documentation and pushed to GitHub), attackers can use it to access the automation platform and potentially reach connected systems.
  • Malicious/impersonating extensions: staff install a lookalike add-on that collects environment data and can open the door to further compromise.

What to do today

  • Brief staff (2 minutes): “If you didn’t start the login, don’t approve anything.” Tell them to report unexpected sign-in prompts immediately.
  • Review Microsoft 365 sign-in alerts for unusual logins and investigate any user reporting unexpected approval requests.
  • Check mail forwarding and mailbox rules for finance, payroll and shared inboxes.
  • If you use n8n (or similar automation): confirm where tokens are stored, rotate any that might have been shared in code/notes, and ensure access is limited to what’s needed.
  • Lock down extensions: ensure only approved extensions are allowed on work browsers/dev machines (especially for anyone handling client data or code).

Ask your IT provider

  • Do we have alerting for suspicious Microsoft 365 sign-ins and repeated approval prompts?
  • Can you quickly produce a report of external mail forwarding and new inbox rules created in the last 7–14 days?
  • Do we control which browser/dev extensions can be installed on company devices?
  • If we use automation tools (like n8n), what’s our process for token management (storage, rotation, offboarding) and how do we prevent secrets being committed to public repos?

Patch watch - only one short paragraph, and only if relevant

If you self-host developer platforms, be aware there is reporting of a serious Gitea issue that could allow file access without logging in on certain versions. This is mainly relevant if you run your own Gitea server internally or expose it to the internet—ask your IT provider to confirm whether you use Gitea and whether it’s been addressed.

One action today

Send a same-day internal message: “Do not approve any Microsoft sign-in/code request you didn’t start—report it immediately,” and have IT review sign-in logs plus external forwarding/inbox rules for finance and shared mailboxes.
