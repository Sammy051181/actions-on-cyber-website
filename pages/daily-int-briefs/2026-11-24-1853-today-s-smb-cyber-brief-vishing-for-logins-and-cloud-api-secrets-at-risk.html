Today’s SMB cyber brief: vishing for logins, and cloud/API secrets at risk

What small and medium-sized businesses should look out for today.

High Tuesday 24 November 2026, 18:53 UK time
Today’s look-out: Vishing-driven account takeovers + cloud/API key exposure (supplier and Azure)

What to look out for today

1) Vishing (phone-based phishing) aimed at stealing logins and MFA approvals. Reporting links a ShinyHunters-associated cluster to vishing campaigns that push staff to type credentials into fake pages and approve sign-ins.

2) Cloud/API secrets exposure and theft. Two separate stories highlight the risk of leaked access keys and stored API credentials being stolen from cloud services or suppliers.

Why this matters to smaller businesses

  • Phone scams bypass email filters. A convincing caller can pressure a receptionist, finance staff member, or busy manager into “quickly” approving a login prompt.
  • Stolen keys don’t need passwords. If API keys, tokens, or cloud access keys leak, attackers may access data or systems directly, sometimes without triggering obvious login alerts.
  • Supplier incidents become your incident. If a vendor you use (security tooling, WAF/CDN, SaaS platforms, AI tools) exposes secrets, attackers may pivot into your accounts or impersonate services.

Warning signs

  • Unexpected phone calls claiming to be from “Microsoft”, “Okta”, your IT provider, your telecoms provider, or a “security team”, pushing urgent action.
  • Requests to approve an MFA prompt you didn’t initiate, or to read out one-time codes.
  • Emails/Teams messages saying “We’re on the phone now” or “I’m from IT” to add pressure and legitimacy.
  • Unusual API/service behaviour: integrations failing, new API keys created, new admin users, new apps connected, or unfamiliar IP locations in audit logs.
  • Supplier notifications about exposed keys/credentials, or “rotate your keys” advisories.

How attackers may exploit the situation

  • Vishing-to-phish: caller persuades a user to enter credentials into a fake login page, then prompts them to approve MFA so the attacker can sign in.
  • Extortion follow-on: once inside, attackers may search for customer data, finance documents, or mailbox access for later leverage and payment fraud.
  • API token abuse: stolen API credentials can be used to pull data, alter integrations, create new secrets, or access connected systems (CRM, finance, analytics, customer portals).
  • Supplier pivot: if a vendor’s customer keys are exposed, attackers may try automated access against customer environments and then move laterally.

What to do today

  • Brief staff (2 minutes): IT/support will never ask you to approve an MFA prompt you didn’t start. If in doubt, hang up and call back using a known number.
  • Turn on and review sign-in alerts for your main identity platform (e.g. Microsoft 365/Google/Okta) and key SaaS tools.
  • Inventory and rotate sensitive keys where feasible: API keys, access tokens, service accounts—prioritise anything tied to customer data, payments, or admin functions.
  • Check logs for the last 7–30 days for new API keys/apps, unusual admin actions, or sign-ins from new locations.
  • Confirm suppliers’ guidance: if any of your providers notify you about key exposure, follow their reset/rotation steps and document what you changed.

Ask your IT provider

  • Do we have a clear call-back and verification process for IT/support requests (so staff can safely challenge callers)?
  • How do we detect and respond to MFA fatigue (repeated prompts) and suspicious sign-ins?
  • Where are our API keys and service account secrets stored, and who can create/rotate them?
  • Do we have alerting for new app consents, creation of new admin accounts, and key changes in our cloud/SaaS tools?
  • If a supplier exposes customer keys, what is our playbook (rotate, revoke sessions, review logs, notify stakeholders)?

Patch watch - only one short paragraph, and only if relevant

Microsoft has warned about exploitation affecting Azure API Management (APIM) Classic tiers involving stolen stored API credentials. If you use Azure APIM (especially Classic), confirm with your IT provider what tier you’re on, whether you’re affected, and whether credentials/secrets were rotated and logs reviewed.

One action today

Send a same-day staff note: “If anyone phones asking you to approve an MFA prompt or share a code/password, hang up and call IT back on a known number.”
